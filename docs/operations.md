# Запуск и эксплуатация

## Локально

Требуется Node.js 22.13+ и npm. В корне проекта:

```powershell
npm install
npm run dev
```

Откройте http://127.0.0.1:5173. API работает на 127.0.0.1:3001. PostgreSQL, Docker и ключи для демо не нужны. Данные сохраняются в `.data/dentlux.sqlite`. Вводите только вымышленные данные. Для пациента используйте вымышленный +7-номер; после запроса код появится под полем. Для сотрудника нажмите «Сотрудникам» и выберите демо-роль: регистратор …01, врач …02, юрист …03, технический админ …04. Полные номера — +77000000001–04.

Для предпросмотра собранной версии:

```powershell
npm run build
npm start
```

Она доступна на http://127.0.0.1:3001. Для записи с этого origin укажите APP_ORIGIN=http://127.0.0.1:3001 в `.env` (скопируйте `.env.example`). Production требует HTTPS.

## Проверки

```powershell
npm test
npm run build
npm run test:e2e
npm run test:load
```

E2E запускает отдельный сервер с чистой SQLite на 3101 и использует установленный Chrome. Если Chrome не установлен: `npx playwright install chromium`, затем `$env:PLAYWRIGHT_CHANNEL='chromium'`. Linux/macOS: `PLAYWRIGHT_CHANNEL=chromium npm run test:e2e`. Dev-сервер для E2E не нужен.

Для PostgreSQL нужен отдельный тестовый database и право создавать схемы:

```powershell
$env:TEST_DATABASE_URL='postgresql://user:password@localhost:5432/dentlux_test'
npm test
Remove-Item Env:TEST_DATABASE_URL
```

Каждый API-тест создаёт случайную схему dentlux_test_* и удаляет только эту схему. Никогда не указывайте production database. Без TEST_DATABASE_URL PostgreSQL-специфичный тест пропускается, остальные выполняются на SQLite.

Нагрузочный тест по умолчанию идёт на API :3001. Для stress: `$env:LOAD_USERS='600'; npm run test:load`. Для другого сервера задайте LOAD_TEST_URL. После смены конфигурации верните переменные в исходное состояние. Нагрузку запускайте только на выделенном демо/тестовом стенде.

## PostgreSQL и HTTPS на сервере

Docker Compose подготовлен для размещения в выбранном клиникой дата-центре Казахстана. Автоматической публикации во внешний хостинг нет.

1. Скопируйте `.env.example` в `.env`, установите NODE_ENV=production и DEMO_MODE=false.
2. Сгенерируйте отдельные секреты DATA_ENCRYPTION_KEY, AUTH_PEPPER, METRICS_TOKEN, POSTGRES_PASSWORD и GRAFANA_PASSWORD: `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`. Пароль Postgres должен быть URL-safe, например hex, так как он используется в connection string.
3. Укажите HTTPS APP_ORIGIN и PUBLIC_URL, SMS_GATEWAY_URL/TOKEN. При необходимости добавьте TELEGRAM_BOT_TOKEN. Добавьте утверждённые STAFF_ACCOUNTS. Для врача укажите doctorId: aida/arman/dana до замены демо-каталога.
4. Установите реальные данные клиники в `backend/catalog.mjs` и контактный телефон в интерфейсе, утвердите согласие и оператора данных. Перед реальными пациентами замените синтетических специалистов/цены и отключите создание демо-аккаунтов. Не используйте демо-данные как фактический прайс.
5. Разместите TLS fullchain.pem и privkey.pem в `infra/tls/` с ограниченными правами. В `infra/secrets/metrics-token` запишите только METRICS_TOKEN. Файлы секретов и сертификатов исключены из Git.
6. Выполните `docker compose up -d --build`. Структура БД и версии миграций создаются при старте. Все DDL первой миграции применяются транзакционно. Изменения триггеров идемпотентны. `npm run db:migrate` применяет ту же схему отдельно.
7. Проверьте HTTPS /api/health, запись с тестовым номером, реальные SMS/Telegram и панели ролей. Демо-коды в production не возвращаются. Сервисы db/app не публикуют порты наружу.
8. Для мониторинга выполните `docker compose --profile monitoring up -d`. Grafana слушает только localhost:3000 (используйте SSH tunnel), Prometheus доступен во внутренней сети. Datasource создаётся автоматически. Правила p95>1s и unavailable находятся в `infra/alerts.yml`; подключите доставку инженеру через Alertmanager/Grafana и проверьте тестовый алерт.

Не запускайте Docker socket в app-контейнере. `.env`, ключи, TLS и бэкапы не включайте в образ или PR. Не задавайте trust proxy на произвольную сеть при прямом доступе к Node: приложение рассчитано на закрытую внутреннюю сеть Nginx.

## Копии и восстановление

Сервис backup создаёт сжатый PostgreSQL dump в `backups/` каждый час. Файлы не удаляются автоматически. Следите за свободным местом, проверяйте свежесть последней копии и копируйте её на отдельный носитель в Казахстане. Секреты шифрования храните отдельно от копий БД; без них восстановить имя и телефон нельзя. Сохраняйте журнал не менее трёх лет согласно ТЗ; политика остальных данных утверждается клиникой.

Восстановление сначала проверяйте в **новой** пустой БД:

```sh
createdb -h HOST -U OWNER dentlux_restore
pg_restore -h HOST -U OWNER -d dentlux_restore --no-owner --exit-on-error backups/dentlux-TIMESTAMP.dump
```

Сверьте количество записей, наличие всех версий schema_migrations, расшифровку тестового пациента, DB-аудит, ограничения слотов и сроки уведомлений. После простоя вручную проверьте очередь: уже неактуальные подтверждения могут потребовать отмены. Переключайте DATABASE_URL только после проверки и согласованного окна остановки; исходную БД сохраните для возврата. Зафиксируйте фактические RPO/RTO. При неудачном релизе откатите образ приложения и верните сохранённую БД; универсального разрушительного down-скрипта миграций нет.

## Импорт старого журнала

Экспортируйте только активные будущие записи в CSV UTF-8 с запятой или JSON. Заголовок CSV:

```csv
phone,name,doctorId,serviceId,date,time,consent
+77005555555,Демо Пациент,aida,consultation,2026-11-02,10:00,true
```

Дата должна быть в ближайших 60 днях, слот — рабочий. `consent=true` означает, что подтверждение согласия уже проверено ответственным лицом; импорт не создаёт его задним числом. Уведомления при импорте отключены. Источники с персональными данными держите вне Git.

```powershell
npm run db:import -- --file bookings.csv
npm run db:import -- --file bookings.csv --commit
```

Первая команда валидирует в настоящей транзакции и откатывает её. Вторая сохраняет весь пакет атомарно. При одной ошибке откатываются все строки. Повторный импорт того же слота завершается конфликтом. Сравните input/validated/committed и число записей с оригиналом; факт переноса 100% реального журнала нельзя подтвердить без исходных данных.
