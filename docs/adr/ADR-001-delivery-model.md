# ADR-001: DentLux жобасы үшін жеткізу моделін таңдау

**Күй (Status):** Қабылданды (Accepted)  
**Күні (Date):** 2026-09-23  
**Шешім қабылдаушылар (Deciders):** Ізбасхан Әселхан (Project Manager), Жандос Арлан (Tech Lead)  
**Техникалық тарих (Technical Story):** DENT-001 — Жоба басқару процесін белгілеу

---

## Контекст және мәселе (Context and Problem Statement)

DentLux — жеке стоматологиялық клиникаға арналған веб-сайт пен онлайн жазылу жүйесі. Жоба мынадай компоненттерден тұрады:

| Компонент | Сипаттама | Белгісіздік деңгейі |
|---|---|---|
| Онлайн жазылу модулі (веб) | Дәрігер таңдау, слот брондау, SMS/email растау | Жоғары — UX форматы тексерілмеген |
| Telegram-бот жазылу | Бот арқылы жазылу, слот тексеру | Жоғары — flow итеративті нақтыланады |
| Дәрігерлер кабинеті | Күнтізбе, жазылуларды қарау/өзгерту | Орташа |
| Əкімшілік панель | Кестелер, статистика, пациент базасы | Орташа |
| Деректер базасы схемасы | PostgreSQL, кестелер, байланыстар | Төмен — ER диаграммасы алдын ала жасалады |
| Инфрақұрылым (CI/CD, Deploy) | Docker, GitHub Actions, хостинг | Төмен — стандартты стек |
| Лендинг бет | Қызметтер, бағалар, команда | Орташа |

**Негізгі проблемалар:**

1. **UX белгісіздігі:** Пациенттер онлайн жазылуда қандай интерфейсті ыңғайлы деп санайды — толық күнтізбе ме, тізімнен таңдау ма, жылдам жазылу ма? Жауап тек пайдаланушы тестілеуінен кейін белгілі болады.
2. **Қос жазылу (double booking) рискі:** Telegram-бот пен веб-сайт бір уақытта бір слотқа жазылуды болдыра ала ма? Бұл архитектуралық шешім жүктеме тестілеуіне байланысты.
3. **MVP шекарасы:** Клиника иесі бастапқыда барлық талаптарды толық тізімдей алмады — минималды жеткілікті функционал итерациялар арқылы анықталады.
4. **Алшақтық:** Деректер базасы схемасы мен инфрақұрылымды Predictive тәсілмен алдын ала жоспарлау мүмкін, бірақ Frontend/Telegram бот — Adaptive тәсілді талап етеді.

Команда: 2 адам. Бюджет: шектеулі. Нарыққа жылдам шығу — бизнес-приоритет.

---

## Шешім драйверлері (Decision Drivers)

1. **Деректер базасы мен инфрақұрылымның тұрақтылығы** — DB схемасы, Docker, CI/CD стегі алдын ала жоспарланып, ерте бекітілуі тиіс; кейінгі өзгерістер migration шығынын арттырады.
2. **Frontend және Telegram-бот икемділігі** — UX пен бот ағыны пайдаланушылар кері байланысы негізінде итеративті жақсартылады; алдын ала толық спецификация мүмкін емес.
3. **MVP жылдам жеткізу** — клиника бәсекелестерінен озу үшін жазылу модулі 4–6 аптада іске қосылуы тиіс.
4. **Сапаны қамтамасыз ету** — слот брондау жүйесінде қате — клиентке тікелей қаржылық шығын; тестілеу итеративті болуы тиіс.
5. **2 адамдық командаға тиімді процесс** — ауыр ceremony-лар (толық Scrum, SRS) артық жүктеме; жеңілдетілген гибридті процесс қажет.
6. **Тапсырыс берушімен үздіксіз байланыс** — клиника иесімен апта сайын демо және приоритет анықтау кездесуі жоспарланған.

---

## Қарастырылған нұсқалар (Considered Options)

### Нұсқа 1: Таза Predictive (Waterfall) — **ҚАБЫЛДАНБАДЫ**

Барлық компоненттер үшін: SRS → Жобалау → Әзірлеу → Тестілеу → Жеткізу. Барлық талаптар алдын ала бекітіледі.

**Шынайы артықшылықтары:**
- Нақты milestone-дар мен бюджет болжауы — кредит немесе инвестор үшін ыңғайлы
- Толық құжаттама — аудит, тендер, заңды дауда қолданылады
- Жоспар бойынша нақты есеп беру — PM жұмысы оңайлайды

**Шынайы кемшіліктері:**
- DentLux UX талаптары бастапқыда толық белгісіз — SRS жазу үшін деректер жоқ → жалған нақтылық
- Клиент пайдаланушылар кері байланысын алғанша 3–4 ай өтеді — нарық мүмкіндігін жіберуіміз мүмкін
- Соңғы кезеңде табылған UX мәселелері жөндеуге өте қымбат (Boehm Cost of Change қисығы)
- Double booking мәселесі тек финалдық тестілеуде анықталады — бұл кеш және қымбат

**Неліктен қабылданбады:** DentLux Frontend/Telegram компоненттері бойынша талаптар итерациялар арқылы ғана нақтылана алады. Таза Waterfall бұл белгісіздікті жабалайды, бірақ жоймайды.

---

### Нұсқа 2: Таза Adaptive (Pure Scrum) — **ҚАБЫЛДАНБАДЫ**

Барлық компоненттер үшін: 2-аптадан спринттер, толық Scrum framework — Product Backlog, Daily Standup, Sprint Review, Retrospective.

**Шынайы артықшылықтары:**
- Жиі жеткізу — клиент 2 аптасайын нәтиже көреді
- Пайдаланушы кері байланысы итерациялар арқылы жылдам енгізіледі
- Команда өзін ұйымдастырады — рухтану жоғары

**Шынайы кемшіліктері:**
- 2 адамдық командада толық Scrum ceremony-лар (Daily + Retro + Review + Planning = апта сайын ~5 сағат) артық жүктеме
- Деректер базасы схемасын «спринт сайын өзгерту» — migration шығыны жоғары, мәліметтер қауіпсіздігі тәуекелі
- Инфрақұрылымды итеративті баптау (Docker, CI/CD) стабильді environment болмайды → developer тәжірибесі нашарлайды
- Product Owner рөлі бекітілмеген — клиника иесі үнемі қол жетімді емес → Backlog приоритеті кешеуілдеуі мүмкін

**Неліктен қабылданбады:** DB/инфрақұрылым компоненттері тұрақты, алдын ала жоспарланған архитектураны талап етеді. Барлығын Adaptive режимінде ұстау — осы компоненттер бойынша артық техникалық қарыз (technical debt) жинайды.

---

### Нұсқа 3: Гибридті модель — Predictive (DB/Инфрақұрылым) + Adaptive (Frontend/Telegram-бот) — **ТАҢДАЛДЫ**

Жобаның екі бөлімі әртүрлі режимде жұмыс істейді:

**Predictive бөлік (Жандос Арлан жетекшілігімен):**
- PostgreSQL деректер базасы схемасы — ER диаграмма + миграциялар алдын ала бекітіледі
- Docker Compose + GitHub Actions CI/CD pipeline — Sprint 1-де баптанады, кейін өзгермейді
- REST API контрактілер (OpenAPI/Swagger) — DB схемасынан кейін бекітіледі

**Adaptive бөлік (Ізбасхан Әселхан жетекшілігімен):**
- Frontend UI/UX — 2-аптадан спринттер, пайдаланушы тестілеуі негізінде итеративті
- Telegram-бот ағыны — спринт сайын пайдаланушы feedback бойынша жақсарады
- Жазылу UX — A/B тестілеу немесе клиника иесімен апта сайын review

**Интеграция нүктесі:** API контракт (Predictive бөлік шығарады) → Frontend/Bot оны тұтынады (Adaptive бөлік)

**Артықшылықтары:**
- DB схемасы тұрақты → migration шығыны минималды
- Frontend итеративті → UX нарыққа сәйкес
- 2 адамдық команда рөлдер бойынша бөлінеді → жүктеме тепе-тең
- CI/CD ерте орнатылады → барлық спринттерде автоматты тестілеу жұмыс істейді

**Кемшіліктері:**
- API контракт өзгерсе — Predictive мен Adaptive бөліктер арасында координация қажет
- Жоспарлау күрделірек — екі режимнің синхронизациясын қадағалау керек

---

## Шешім (Decision Outcome)

**Таңдалған нұсқа: Гибридті модель (Predictive + Adaptive)**

### Компоненттер бойынша модель бөлінісі

| Компонент | Модель | Жауапты | Негіздеме |
|---|---|---|---|
| PostgreSQL схемасы + миграциялар | **Predictive** | Жандос Арлан | Кейінгі schema өзгерістері data migration шығынын арттырады |
| Docker Compose + GitHub Actions | **Predictive** | Жандос Арлан | Тұрақты environment барлық спринттерге қажет |
| REST API контрактілер (OpenAPI) | **Predictive** | Жандос Арлан | Frontend/Bot контрактіні білу керек |
| Frontend UI/UX (React) | **Adaptive** | Ізбасхан Әселхан | UX итеративті пайдаланушы feedback бойынша |
| Telegram-бот ағыны | **Adaptive** | Ізбасхан Әселхан | Бот сценарийлері пайдаланушы тестілеуінде нақтыланады |
| Онлайн жазылу модулі | **Adaptive** | Ізбасхан Әселхан | Жазылу flow MVP-дан кейін жақсарады |

### Операциялық конфигурация

- **Спринт ұзақтығы:** 2 апта
- **Міндетті ceremony-лар:** Sprint Planning + Sprint Review (2 аптасайын, 45–60 мин)
- **Ұсынылатын:** Retrospective (айына 1 рет, 30 мин)
- **Шұғыл тапсырмалар:** GitHub Projects Kanban арнасы арқылы, спринт goal-ды өзгертпей
- **Клиентпен байланыс:** Апта сайын 30 мин Priority Review + Sprint Review демосы

## Салдарлар (Consequences)

### Жағымды салдарлар

- **DB тұрақтылығы:** Схема алдын ала бекітілгендіктен, migration шығыны минималды — деректер қауіпсіздігі жоғары
- **MVP жылдам жеткізу:** Frontend Adaptive режимінде — жазылу модулі 4–6 аптада жұмыс істейді
- **Double booking ерте анықталады:** CI pipeline итеративті интеграциялық тестілеу жүргізеді
- **Тиімді жүктеме бөлінісі:** Жандос — DB/инфра алдын ала, Әселхан — UI итеративті
- **CI/CD Sprint 1-де дайын:** Барлық кейінгі спринттерде автоматты тестілеу жұмыс істейді

### Жағымсыз салдарлар және не жоғалтамыз

| Жағымсыз салдар | Не жоғалтамыз | Жеңілдету жолы |
|---|---|---|
| API контракт өзгерсе — фронтенд тоқтауы мүмкін | Adaptive бөліктің жұмыс жылдамдығы төмендейді | API контракт өзгерісі — ADR арқылы ресімделеді, екі жақ бір мезгілде хабардар болады |
| Predictive бөліктегі DB қателер кеш анықталса | Schema migration — қымбат және уақытты алады | ER диаграмма Sprint 0-де review өтеді; DB тест ортасы ерте орнатылады |
| Гибридті жоспарлаудың күрделілігі | PM жоспарлауға қосымша уақыт жұмсайды | GitHub Projects кастом өрістері (Component, Sprint, Model) визуализация жасайды |
| Ceremony-ларды өткізіп жіберу | Ретроспектив болмаса — командадағы мәселелер жиналады | Calendar-да алдын ала бекітілген; Sprint Review — клиентпен бірге, өткізу қиын |
| Толық Waterfall документациясының болмауы | Болашақта аудит немесе команда ауысуы кезінде контекст жоғалуы мүмкін | ADR жүйесі + README + API doc жеткілікті деңгейде контексті сақтайды |
