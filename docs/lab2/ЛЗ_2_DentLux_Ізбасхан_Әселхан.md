## 1-БӨЛІМ. Үш кейс үшін жеткізу моделін таңдау және салыстырмалы талдау

### 1.1 Кейстердің сипаттамасы

**Кейс А: Тендер бойынша мемлекеттік органда құжат айналымы АЖ-ны енгізу**
Мемлекеттік тапсырыс беруші тендер арқылы жеңімпаз анықтап, ТЗ-ны (техникалық тапсырма) алдын ала толық бекіткен. Талаптарды өзгерту — ресми Change Request процедурасы, заңнамалық регуляция мен аудит міндетті. Жүйе — электрондық құжат айналымы (ЭЦҚ интеграциясы, архив, маршруттау, рөлдер). Deliverable: толық аяқталған жүйе + пайдалануға беру акті.

**Кейс Ә: Тексерілмеген гипотезасы бар стартаптың жаңа мобильді өнімі**
Стартап команда нарықта ұқсас өнім жоқ деп болжайды, бірақ пайдаланушылардың нақты қажеттіліктері тексерілмеген. MVP арқылы гипотезаны растау немесе жоққа шығару — бастапқы мақсат. Талаптар итерация сайын түбегейлі өзгеруі мүмкін. Pivot мүмкіндігі жоғары.

**Кейс Б: Банк монолитін бұлтқа көшіру**
Ірі банктің жұмыс істеп тұрған монолитті core banking жүйесін AWS/Azure бұлтына migrate ету. Регулятор (ҚР ҰБ, АРРФР) талаптары қатаң: 99.95% SLA, деректер локализациясы, аудит логтары. Техникалық тәуекел өте жоғары — миграция кезеңінде production жүйесі тоқтамауы тиіс. Жоба ірі, командалар бірнешеу.

### 1.2 Жеткізу моделін таңдау нәтижесі

| Кейс | Таңдалған модель | Негіздеме |
|---|---|---|
| Кейс А: Мем. АЖ | **Predictive (Waterfall)** | ТЗ бекітілген, өзгерістер ресми процедурамен, аудит үшін толық құжаттама міндетті |
| Кейс Ә: Стартап мобильді өнімі | **Adaptive (Continuous Discovery + Lean Startup)** | Гипотеза тексерілмеген, pivot жиі болады, нарыққа жылдам шығу критикалық |
| Кейс Б: Банк монолитін бұлтқа | **Hybrid (Predictive фазалар + Agile итерациялар)** | Регулятор талаптары қатаң (predictive жоспар керек), бірақ миграция кезеңдері итеративті тестілеуді талап етеді |

### 1.3 Алты өлшем бойынша салыстыру кестесі

| Өлшем | Кейс А: Мем. АЖ (Predictive) | Кейс Ә: Стартап (Adaptive) | Кейс Б: Банк миграциясы (Hybrid) |
|---|---|---|---|
| **1. Талаптардың тұрақтылығы** | Өте жоғары — ТЗ тендерге дейін бекітілген, өзгерту Change Request + комиссия мақұлдауы арқылы | Өте төмен — гипотезалар user interview, A/B тесттер нәтижесінде спринт сайын қайта қаралады | Орташа — регулятор талаптары тұрақты, бірақ cloud-архитектура шешімдері итеративті нақтыланады |
| **2. Жеткізу жиілігі** | Сирек — фаза milestone-дары бойынша (3–6 айда бір рет), финалдық deliverable жобаның соңында | Өте жиі — 1–2 апталық sprint, апта сайын тестілеуге жаңа build; «ship daily» мәдениеті | Орташа — миграция толқындары (wave) квартал сайын, ішкі итерациялар 2 апта |
| **3. Тәуекел профилі** | Орта-жоғары: тестілеу тек соңында, кеш табылған қате қымбатқа түседі; регулятор рискі — өтпесе, жоба тоқтайды | Жоғары бизнес-риск: нарыққа шықса да өнім сатылмауы мүмкін; техникалық риск төмен (MVP кішігірім) | Критикалық операциялық риск: production банк жүйесі тоқтаса — тікелей қаржылық шығын + регулятор санкциясы |
| **4. Тапсырыс берушімен өзара әрекет** | Формалды, кезеңді — kick-off, milestone review, UAT, сдача-приёмка актілері; күнделікті байланыс жоқ | Тығыз, үздіксіз — product owner командада, user interview апта сайын, демо сайын | Аралық — Steering Committee ай сайын, техникалық working group апта сайын, операциялық команда онлайн |
| **5. Команда құрылымы мен масштабы** | Иерархиялық: PM, аналитик, архитектор, девелоперлер, тестер — рөлдер қатаң бөлінген, жауапкершілік матрицасы RACI | Кішігірім, кросс-функционалды: 3–6 адам, барлығы «full-stack мойынсынады», T-shaped компетенциялар | Бірнеше команда: Platform team, Migration team, Testing team, Security team — координация SAFe/LeSS арқылы |
| **6. Сәттілік өлшемі** | Scope, Time, Cost — «темір үшбұрыш»; ТЗ-дан ауытқу — келісімшарт бұзылуы | Validated learning — гипотеза расталды ма? Retention, conversion метрикалары; pivot немесе persevere шешімі | Нөлдік downtime миграция; SLA сақталуы; регулятор аудитінен өту; TCO азаюы |

### 1.4 Таңдаулардың негіздемесі

**Кейс А → Predictive:**
Мемлекеттік тендер жобасында барлық талаптар заңды күші бар ТЗ-да бекітілген. Жеткізу жоспары келісімшартқа кіреді. Auditable deliverable-дар (актілер, хаттамалар, тест есептері) міндетті. Agile итерациялары бұл контексте заңды рәсімге сәйкес келмейді — тапсырыс беруші «жұмыс жасалып жатқан бағдарламалық жасақтама» емес, бекітілген milestone-дарды күтеді.

**Кейс Ә → Adaptive:**
Тексерілмеген гипотеза — бұл жобаның өзегі. Lean Startup циклі: Build → Measure → Learn. Алдымен толық жоспар жасаудың мәні жоқ, себебі 3-спринттен кейін өнімнің бағыты түбегейлі өзгеруі мүмкін. Adaptive модель бұл белгісіздікті артықшылыққа айналдырады — команда жылдам оқып, жылдам бейімделеді.

**Кейс Б → Hybrid:**
Банк миграциясы екі полюсті талап етеді. Predictive жағы: регулятор үшін толық Migration Plan, Rollback Plan, Risk Register алдын ала бекітілуі тиіс. Agile жағы: нақты cloud-архитектура шешімдері (қай сервисті бірінші migrate ету, қандай pattern қолдану) тек нақты тестілеу нәтижесінде анықталады. Сондықтан Hybrid — фазалық predictive жоспар + ішкі Agile спринттер.

## 3-БӨЛІМ. GitHub Projects жұмыс кеңістігі мен тапсырмаларды ұйымдастыру

### 3.1 Kanban/Scrum тақтасының құрылымы

GitHub Projects ішінде **"DentLux — Sprint Board"** тақтасы мынадай бағандармен конфигурацияланады:

| Баған | Мақсаты | WIP Limit | Ауысу шарты |
|---|---|---|---|
| **📋 Backlog** | Барлық жоспарланған тапсырмалар, приоритет бойынша реттелген | Шектеусіз | PM қосады |
| **🔍 Ready for Dev** | Sprint Planning-де таңдалған, DoR тексерілген | Макс. 6 | Sprint Planning кезінде |
| **⚙️ In Progress** | Белсенді жұмыс жасалып жатқан | Макс. 3 | Орындаушы өзі жылжытады |
| **👁️ Code Review / QA** | PR ашылған, review немесе QA тестілеу | Макс. 4 | PR ашылғанда автоматты |
| **✅ Done** | DoD толық орындалған, merge болған | Шектеусіз | PR merge + DoD чек-лист |

**Кастом өрістер (Custom Fields):**
- `Sprint` — қай спринтке жатады (Sprint 1, Sprint 2…)
- `Story Points` — күрделілік бағасы (1, 2, 3, 5, 8, 13)
- `Priority` — P0/P1/P2/P3
- `Component` — frontend / backend / database / devops / integration

### 3.3 Branching Strategy (GitFlow)

#### Негізгі веткалар

| Ветка | Мақсаты | Ереже |
|---|---|---|
| `main` | Production-ready код | Тек `release/*` немесе `hotfix/*` арқылы merge |
| `develop` | Интеграция ветка | Барлық `feature/*` осюда merge болады |

#### Жұмыс веткалары — аталдыру форматы

| Тип | Формат | Мысал |
|---|---|---|
| Feature | `feature/dent-{N}-{slug}` | `feature/dent-12-auth-page` |
| Bug Fix | `fix/dent-{N}-{slug}` | `fix/dent-45-calendar-bug` |
| Hot Fix | `hotfix/dent-{N}-{slug}` | `hotfix/dent-67-double-booking` |
| Release | `release/v{major}.{minor}` | `release/v1.0` |
| Refactor | `refactor/dent-{N}-{slug}` | `refactor/dent-23-slot-service` |

```
# Дұрыс:
feature/dent-12-auth-page          ✅
fix/dent-45-calendar-double-slot   ✅
hotfix/dent-67-sms-timeout         ✅

# Дұрыс емес:
my-branch           ❌  issue нөмірі жоқ
Feature/Auth        ❌  бас әріп
fix_45_bug          ❌  дефис орнына астын сызу
dent45              ❌  тип жоқ
```

### 3.4 PR ережелері және Definition of Done

#### PR ашу шарттары (Definition of Ready for Review)
- [ ] Ветка атауы стандартқа сәйкес
- [ ] Commit хабарламалары Conventional Commits форматында: `feat(booking): add slot reservation endpoint`
- [ ] ESLint / Prettier (frontend), Flake8/Black (backend) — нөл қате
- [ ] Unit тесттер жазылған (жаңа функционал үшін)
- [ ] CI pipeline (GitHub Actions) жасыл
- [ ] PR шаблоны толтырылған
- [ ] Reviewer тағайындалған (Жандос ↔ Әселхан cross-review)

#### PR шаблоны `.github/pull_request_template.md`

```markdown
## 🔗 Байланысты Issue
Closes #__

## 📝 Өзгерістер сипаттамасы

## 🧪 Тестілеу нұсқаулығы
1. 
2. 

## ✅ PR Чек-листі
- [ ] Линтер қатесіз өтті
- [ ] Unit тесттер жазылды / жаңартылды
- [ ] CI/CD pipeline жасыл
- [ ] Ветка аталдыру стандарты сақталды
- [ ] Reviewer тағайындалды
- [ ] Скриншот / видео (UI өзгерісі болса)
```

#### Definition of Done (DoD) чек-листі

**Код:**
- [ ] `develop` ветқасына merge болды
- [ ] Code Review кемінде 1 Approve
- [ ] Линтер — нөл қате

**Тестілеу:**
- [ ] CI автотесттер өтті
- [ ] QA manual тестілеу жүргізілді
- [ ] Acceptance Criteria барлығы орындалды

**Құжаттама:**
- [ ] README / API doc жаңартылды (қажет болса)
- [ ] ADR жазылды (архитектуралық шешім болса)

**Жеткізу:**
- [ ] `staging` ортасына deploy болды
- [ ] Sprint Review-ға дайын
